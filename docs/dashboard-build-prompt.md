### 2. 먼저 확인할 사실

아래는 작성 시점의 코드·문서 근거다. 실행 시 다시 확인하고 바뀐 사실을 우선하라.

- 기존 대시보드는 목 데이터이며 실제 API·DB·사용자 계정에 연결되지 않았다. 기간 버튼이 날짜 라벨만 바꾸는지, 메뉴가 같은 화면을 계속 보여주는지까지 확인하라.
- 본 시스템에는 `/api/admin/metrics`, `/api/admin/export.csv`, `/api/orgs/{org_id}/members`, `/api/orgs/{org_id}/sessions` 등이 존재한다. 인증, 기관 범위, 날짜 필터, 페이지네이션을 실제 코드로 검토하라. 전역 관리자 집계를 기관 관리자 화면에 그대로 연결하지 말라.
- 본 시스템 개인 세션·리포트에는 `X-Session-Token` 계약이 있다. 관리자 열람은 서버에서 관리자 권한으로 별도 검증해야 하며 방문객 토큰을 수집·공유하는 방식으로 구현하지 말라.
- 키오스크에는 NFC 등록·조회, 출력 작업 조회, 실제 리포트 연결 코드가 있다. 방문객 `/api/*`는 loopback 제한이고 원격 bridge API는 서버 간 토큰을 요구한다. 대시보드 브라우저에서 제한을 우회하거나 비밀을 전달하지 말라.
- `integrations/mirrorting/session_bridge.patch`는 별도 스냅샷용 패치다. 본 시스템에 적용됐다고 가정하지 말고 현재 대상 코드·DB에 맞는지 확인하라. `/Users/do_not_delay/Downloads/2026CarpeDM_EXPO-main`은 다른 수정된 체크아웃일 수 있으므로 두 사본을 섞지 말라.
- 사원증의 개발·AI·디자인·기획·마케팅·인사 팀과 본 시스템의 체험 직무는 별개다. 자동 매핑하지 말라.
- 공식 4-Fit은 **Response/응답, Voice/목소리, Expression/표정, Posture/자세**다. `eye`는 보조 관측값이며 다섯 번째 점수 축으로 추가하지 말라. 참고·잠정 평가 표기는 보존하라.
- 설정 존재, HTTP 응답 성공, 소프트웨어 테스트 통과, 물리 장치 동작 확인을 서로 구분하라.

우선 짧은 현황표를 작성하라: 기능 / 원천 파일·API / 현재 상태 / 부족한 계약 / 이번 구현 범위. 상태는 `코드 있음`, `소프트웨어 검증`, `실물 검증 필요`, `미연동`, `제안`을 구분하라. 필요한 정보를 코드에서 찾을 수 있으면 질문 없이 진행하라. 실제로 막히는 사항만 질문하고 독립 작업은 계속하라.

### 3. 제품 목표와 정보 구조

운영자가 다음 세 가지를 5초 안에 파악할 수 있어야 한다: 지금 체험이 어떻게 진행되는가, 어느 장치·작업이 막혔는가, 다음에 무엇을 해야 하는가.

기본 메뉴는 아래 여섯 개이며 각각 실제 내용·URL·새로고침·뒤로가기가 동작해야 한다. 반복 화면과 눌러도 안내 토스트만 나오는 가짜 기능을 완료 처리하지 말라.

1. **운영 개요**: 조회 기간·기관 범위·데이터 모드, 주요 집계, 장치 요약, 확인할 장애, 최근 체험.
2. **체험 세션**: 익명 참여 ID, 사원증 소속 팀, 체험 직무·시나리오, 시작·종료 시각, 현재 단계, 연결 상태, 결과 상태. 검색·필터·정렬·페이지네이션·상세 화면.
3. **4-Fit 리포트**: 네 관점의 결과, 분석 근거·엔진 버전·참고 평가 표시, 강점·연습 제안. 조직 집계와 개인 상세의 권한을 분리하라.
4. **장치·출력**: 미러·키오스크·NFC·프린터·분석 서비스의 확인 가능한 상태와 마지막 확인 시각, 배지·리포트 작업 이력.
5. **오류·복구 기록**: 오류 코드, 영향받은 세션·작업, 발생·최근 확인 시각, 재시도 가능 여부, 복구 안내와 처리 이력.
6. **운영 설정**: 조회 권한, 데이터 원천·연결 검사, 새로고침 주기, 보관 정책과 배포 정보. 실제 설정 API가 없는 항목은 읽기 전용으로 표시하라.

기관별 훈련 현황은 운영 개요·리포트 안에서 실제 등록 회원·체험 데이터를 기준으로 제공하라. 사원증을 발급받은 방문객을 기업의 재직 직원으로 단정하지 말라. 근거 없는 팀별 인원·참여율·역량 상승 수치를 제거하라.

핵심 상세 화면은 **등록 → NFC 연결 → 역할극 → 분석 → 리포트 → 출력** 타임라인이다. 서로 다른 저장소의 상태를 대응표로 정규화하고 원래 상태도 확인할 수 있게 하라. kioskSessionId와 mirrorSessionId는 별개이며 검증된 연결 키로만 이어라. 연결이 없으면 `미연동`으로 표시하고 이름·팀·시간 유사도로 임의 결합하지 말라.

### 5. 데이터와 연동

기존 React/Vite·native CSS와 설치된 도구를 우선 사용하라. 필요한 타입·런타임 검증을 경계에 적용하되 언어·프레임워크 전체 교체나 새 상태 관리 라이브러리는 피하라. 서버는 기존 FastAPI 계약을 재사용하고, 부족한 원천 조회에는 인증된 서버 간 집계 계층을 최소한으로 추가하라. 원천 DB를 브라우저에 공개하거나 대시보드용 평행 사용자·세션 DB를 불필요하게 만들지 말라.

실제 API와 고정 시연 데이터는 동일한 명시적 데이터 계약을 따르게 하라. `실제 데이터`와 `EXPO 시연 데이터` 모드는 URL/서버 설정·상단 라벨로 구분하고 시연 데이터는 별도 seed/fixture로 보관하라. 실제 요청 실패를 목 성공으로 대체하지 말라. 시연 모드에서는 실물 출력·원천 변경을 차단하고, 오류·미연동도 시연할 수 있게 하라.

없는 관리자 API는 먼저 원천 계약을 확인한 뒤 새로 정의하고 문서·인증·테스트를 함께 구현하라. 관리자가 세션·작업 목록을 읽는 경로와 방문객 API를 분리하라. loopback 또는 bridge 제한을 풀어 대시보드를 연결하지 말라. 원격 관측 경로가 없으면 최소한의 인증된 읽기 전용 계약을 추가하거나 `관측 미연결`로 표시하라.

운영 갱신은 수동 새로고침과 제한된 주기 폴링부터 시작하라. 이전 요청 취소, 늦게 도착한 응답 무시, 숨겨진 탭에서 폴링 중지, 오류 시 지연 재시도, 마지막 성공 시각을 구현하라. 네트워크 끊김 때 이전 값을 보여주더라도 `갱신 지연`을 표시하라. API가 살아 있다고 카메라·마이크·NFC·용지 상태까지 정상으로 표시하지 말라. 센서·용지 텔레메트리가 없으면 `확인 불가`다.

집계 규칙을 데이터 계약에 명시하라.

- 체험 건수와 고유 참여자 수를 구분하고 같은 세션의 갱신·재시도로 중복 집계하지 말라.
- 참여율은 등록 대상자·참여자의 정의와 분모가 있는 경우에만 계산하라. 방문객 수를 기관 직원 수로 사용하지 말라.
- 완료율·분석 성공률·출력 확인율은 서로 다른 상태와 분모를 사용하라.
- 누락 점수는 `null/미측정`이며 0점이 아니다. 평균은 유효 표본만 계산하고 표본 수·관측 비율을 함께 보여라.
- 전후 변화는 같은 참여자·시나리오·평가 엔진 등 비교 조건이 충족되는 실제 기록만 사용하고 학습 효과 입증으로 표현하지 말라.
- 화면과 CSV가 같은 기간·기관·상태 필터를 사용하게 하라. 서버에서 필터링·집계·페이지네이션하고 기본 조회 상한을 두어라.
- 저장 시각은 UTC, 화면은 Asia/Seoul을 기본으로 하며 조회 구간 경계와 타임존을 명시하라. 표본이 없거나 분모가 0이면 의미에 맞게 `데이터 없음`을 보여라.

### 6. 출력과 복구의 안전 기준

기존 키오스크 계약을 보존하라. 작업 상태 `running/success/retryable_error/unknown/error`와 출력 결과 `preview/submitted/confirmed`를 별도로 모델링하라.

- `preview`: 화면 미리보기이며 실물 출력이 아니다.
- `submitted`: 프린터에 전송했지만 종이 배출 확인이 아니다.
- `confirmed`: 권한 있는 현장 운영자가 실물을 확인한 상태다.
- `unknown`: 결과를 알 수 없다. 자동 재출력하지 말고 현장 확인을 안내하라.

HTTP 200이나 작업 success만으로 `출력 완료`라고 표시하지 말라. 안전한 재시도는 기존 operationId를 유지하고 중복 클릭·네트워크 재전송·서버 재시작에도 중복 출력을 막아라. 카드가 재발급되거나 세션이 달라지면 과거 리포트를 새 방문객에게 연결하지 말라.

첫 버전은 읽기 전용 상태·복구 안내를 우선 완성하라. 기존 CLI만 있는 복구를 가짜 UI 버튼으로 대체하지 말라. 재분석·출력 결과 확인·카드 폐기 등 변경 기능을 노출하려면 권한, 대상·영향 확인, 사유 입력, 서버 검증, 감사 기록을 함께 구현하라. 안전한 원천 계약이 없으면 기능을 숨기거나 비활성화하고 이유를 표시하라. 전역 reset을 세션 하나의 초기화 버튼처럼 사용하지 말라.

### 7. 실제 운영을 위한 최소 보안·안정성

기존 인증·기관 모델을 먼저 재사용하라. 필요한 권한은 운영자·기관 관리자·시스템 관리자이며, 메뉴 표시뿐 아니라 서버에서 조회·상세·CSV·변경 작업을 모두 검사하라. 화면용 권한 이름은 기존 역할에 매핑하고 중복 계정 체계를 만들지 말라. 기관 관리자는 자기 기관 데이터만 조회하며 URL·ID·필터 변조로 다른 기관에 접근할 수 없어야 한다.

브리지 토큰·운영 공용 토큰은 서버 환경에만 보관하고 `VITE_*`, 번들, URL, 브라우저 저장소, 응답·로그에 넣지 말라. 기존 인증을 검토해 세션 만료·로그아웃을 처리하고, 쿠키 인증을 사용하면 Secure/HttpOnly/SameSite와 변경 요청 CSRF 방어를 적용하라. 운영 모드에서 무인증 관리 경로·개발 우회가 열리면 시작 또는 접근을 거부하라.

기본 화면은 익명 ID와 집계다. 이름·원문 발화·사진·음성·카드 UID는 필요한 권한과 목적이 있을 때만 최소한으로 제공하라. 기존 보관기간·익명화·삭제 동작을 보존하고 대시보드 캐시·감사 로그·CSV에도 적용하라. 개인정보가 만료돼도 중복 출력 방지에 필요한 최소 작업 이력은 임의 삭제하지 말라. CSV의 수식 실행 위험을 막고 공개 시연에서는 실제 방문객 정보를 사용하지 말라.

입력 검증, 허용된 서버 주소, 외부 요청 타임아웃, 오류 코드, 페이지 크기 제한, 감사 로그의 비밀값 제거를 구현하라. 필요한 스키마 변경은 기존 DB 백업·마이그레이션·복원 절차와 함께 제공하라. 개발·테스트·운영 환경을 분리하고 `.env.example`, 실행 순서, 상태 확인, 최소 백업·복구·롤백 절차를 남겨라. 실환경 백업 복원은 별도 승인 없이 하지 말고 테스트 DB로 검증하라.

결제·구독·CRM·Kubernetes·새 메시지 큐·마이크로서비스·새 LLM·카메라 분석 엔진은 이번 범위에 추가하지 말라. 사업 확장에 필요한 미구현 항목은 발생 조건과 함께 TODO로 남겨라.

### 8. 실행 순서와 완료 조건

이 순서로 진행하되 매 단계에서 사용자 확인을 기다리며 멈추지 말라. 첫 화면만 다듬고 끝내지 말라.

1. 저장소·계약을 점검하고 변경 파일과 이유를 짧게 설명하라.
2. 실제 가능한 데이터 계약과 화면 구조를 확정하고 고정 시연 데이터를 분리하라.
3. 여섯 메뉴와 핵심 세션 타임라인을 구현하라. 조회·필터·상세·CSV·권한·오류 상태를 연결하라.
4. 실제 백엔드의 안전한 관리자 조회를 연결하고 필요한 최소 연동 패치를 검증하라. 안전한 변경 기능만 활성화하라.
5. 자동 검사와 실제 브라우저 검증을 수행하고 실패를 수정하라.
6. README·API·지표 정의·운영 절차·검증 기록을 실제 구현과 맞춰라.

필수 검증은 다음과 같다.

- 대시보드 build와 실제 존재하는 lint/typecheck를 실행하라. 스크립트가 없으면 적절한 최소 검사를 추가하거나 미실행 이유를 기록하라. API 변경 시 해당 저장소의 기존 테스트를 실행하라.
- 하나의 테스트 세션이 등록·연결·체험·결과·작업 상세에서 같은 대상으로 이어지는지 확인하라. 카드 재사용과 늦은 응답이 다음 방문객에게 누출되지 않는지 확인하라.
- 기간/기관 변경이 모든 표·차트·CSV에 일치하는지, 누락 점수가 평균에 0으로 들어가지 않는지, 새로고침·직접 URL·뒤로가기가 동작하는지 확인하라.
- 미인증·타 기관 접근·세션 만료·CSV 권한 거부를 서버 테스트로 확인하라.
- 데이터 없음·일부 지표 미측정·API 지연·단절·분석 실패·미연동·unknown 출력·중복 요청·서버 재시작을 테스트하라. 자동 재출력은 발생하면 안 된다.
- 360/390/768/1024/1280/1440px와 기존 시연 화면 1518×750에서 주요 화면을 실제 렌더링하라. 작은 화면에서 표는 핵심 열과 상세 진입 또는 명시적인 표 내부 스크롤을 제공하라.
- 키보드 탐색·200% 확대·reduced-motion·브라우저 콘솔·내부 링크를 확인하고 대표 스크린샷을 저장하라. 도구로 확인하지 못한 항목은 미검증으로 기록하라.
- 테스트 DB의 백업·마이그레이션·복원과 깨끗한 환경의 실행 절차를 확인하라. 사용 가능한 장치가 없으면 NFC·실물 출력·Pi/Windows 현장 검증을 통과했다고 쓰지 말라.

시연 시나리오는 `오늘 운영 확인 → 세션 추적 → 실제 또는 명시적 예시 리포트 → 출력 상태 구분 → 장애 원인·복구 안내 → 권한 있는 CSV 내보내기`다. 실행 명령과 준비물을 문서화하고 실제 데이터 모드와 시연 모드를 혼동하지 않게 하라.

최종 보고는 **현재 문제 요약 → 수정 방향 → 수정 파일 목록 → 적용한 최종 코드/파일 → 실행 방법 → 실제 테스트와 결과 → 예상 결과 → 추가 개선** 순으로 작성하라. `UI 완료 / 실제 API 연동 / 자동 검증 / 현장 장치 검증 / 공개 배포 / 기관 운영 준비`를 별도 상태로 보고하라. 숫자·수상·고객·매출·효과를 만들지 말고, 확인하지 못한 배포·연동·보안·실물 검증을 근거 없이 완료 처리하지 말라.

## 작성 시 확인한 근거

- 기존 대시보드 `README.md`는 목 데이터이며 API·DB·실제 계정 미연결이라고 명시한다. `src/App.jsx`에는 고정 팀 수치·기간과 화면 데이터 CSV 생성이 있다.
- 키오스크 `docs/API_CONTRACT.md`, `backend/app.py`, `docs/OPERATIONS.md`에서 NFC·출력·bridge 경로, loopback 제한, 출력 상태와 복구 계약을 확인했다.
- 키오스크 `integrations/mirrorting/README.md`는 동반 패치가 원본 서버에 미적용이며 다른 스냅샷을 기준으로 작성됐다고 명시한다. `/Desktop/EXPO`의 세션 코드·설정에서 해당 bridge 필드를 찾지 못했다. 실제 배포 대상은 다시 확인해야 한다.
- 본 시스템 `poc/backend/app/api/admin.py`, `orgs.py`, `deps.py`, 모델·스키마에서 관리자 집계·기관 조회·권한·세션 토큰·네 점수 축과 eye 관측값을 확인했다. 전역 관리자 집계와 기관별 조회는 다른 계약이다.
- 마이크로사이트 `docs/product.md`는 직장 대화 연습을 주 시나리오로 지정하고 분석·연동의 확인 범위를 구분한다.
